## AI QUICK CONTEXT (START)

| Dimension | Value |
|---|---|
| **Project Name** | Distributed Job Scheduling & Task Execution Platform (Maven artifact `com.distributed:job-platform:1.0.0`) |
| **Project Purpose** | Multi-user REST platform where users submit background jobs; a DB-backed scheduler admits due jobs into a priority-ordered in-memory dispatch queue; a bounded worker pool atomically claims jobs from PostgreSQL and executes them with retry, exponential backoff, timeout detection, DEAD-state handling, admin recovery, idempotent job creation, JWT auth, Redis rate limiting, Kafka lifecycle events persisted to an audit table, and Prometheus/Grafana observability |
| **Architecture** | Modular monolith (single Spring Boot app). Asynchronous job processing via DB as source of truth + `@Scheduled` poller + `ThreadPoolExecutor` workers. Kafka used for **event propagation/audit only**, NOT as the task queue |
| **Backend** | Java 17, Spring Boot 3.2.5, Spring Web MVC, Spring Data JPA (Hibernate), Spring Security, Spring Kafka 3.1.4, Spring Data Redis, Spring Actuator + Micrometer, springdoc-openapi 2.5.0, JJWT 0.12.5 |
| **Frontend** | React 18 + Vite 5 + react-router-dom 6.22 + Tailwind CSS 3.4 (JSX, no TypeScript), dev-server proxy `/api → localhost:8080` |
| **Database** | PostgreSQL 16 (source of truth for jobs, attempts, results, idempotency keys, audit events, users). Schema generated by Hibernate `ddl-auto=update`. H2 in-memory used for tests |
| **Cache** | Redis 7 — used for **rate limiting only**. Redis is NOT the source of truth for job state (verified: no job data is ever written to Redis) |
| **Messaging** | Apache Kafka 3.6 (KRaft, single broker, topic `job-lifecycle-events`, 3 partitions). At-least-once. Consumer group `job-platform-audit-consumer` persists events to `job_audit_events` idempotently by `eventId` |
| **Scheduler** | Spring `@Scheduled(fixedDelayString = "${app.scheduler.interval-seconds:5}", initialDelay = 5000)` on `JobScheduler.scheduleDueJobs()`. **⚠ Discrepancy: Spring reads this value as MILLISECONDS → the loop actually fires every 5 ms, not every 5 s (see §14 and §56)** |
| **Queue** | NOT a durable queue. PostgreSQL holds job state; ordering happens in SQL (`ORDER BY priority ASC, scheduledAt ASC NULLS LAST`); dispatch buffer is the executor's in-memory `LinkedBlockingQueue(100)` plus a per-instance `ConcurrentHashMap.newKeySet()` dedup guard |
| **Worker Model** | `ThreadPoolExecutor(core=max=5, LinkedBlockingQueue(100), CallerRunsPolicy)`, named threads `job-worker-N`, core-thread timeout 60 s, graceful `@PreDestroy` shutdown (30 s), then `shutdownNow()` |
| **Security** | JWT (HS256, JJWT), stateless sessions, BCrypt password hashing, roles USER/ADMIN, per-record ownership checks returning 404 (no existence leak), registration hard-coded to create USER only, admin endpoints enforced at URL level AND via `@PreAuthorize` |
| **Observability** | Micrometer counters/gauges/timer + `@Timed` (TimedAspect registered) → `/actuator/prometheus` → Prometheus (15 s scrape) → Grafana 10.4 (provisioned dashboard "Job Platform Overview", 10 panels) |
| **Testing** | JUnit 5 + Mockito. **128 `@Test` methods** in 8 classes; Surefire reports in `target/surefire-reports/` show `Tests run: 128, Failures: 0, Errors: 0, Skipped: 0` across all 8 classes — matching the README claim exactly |
| **Runtime** | `e2e_verify.py` (stdlib-only Python) executes scenarios A–K against the live Docker stack. README documents 15/15 PASS with DB/Kafka/Redis/Prometheus evidence. Script-level assertions exist for all scenarios except J (Kafka audit), which explicitly defers to manual `psql` verification |
| **Major Features** | 9-state guarded state machine; atomic QUEUED→RUNNING claim via conditional UPDATE; automatic retry with exponential backoff (1s→30s cap); cooperative timeout detection; retries-exhausted→DEAD; admin recovery DEAD→QUEUED; owner-scoped request idempotency with concurrent-race resolution; Redis sliding-window rate limiting (atomic Lua, fail-open, 429+headers+metric); 8 Kafka lifecycle event types → idempotent audit table |
| **Major Limitations** | At-least-once execution only (NOT exactly-once); cooperative (non-forced) interruption on timeout; single-instance scheduler with no distributed lock; in-memory dispatch queue (DB is recovery source); all handlers are SIMULATED (sleeps/random results, no external integrations); scheduler interval unit discrepancy (5 ms actual vs 5 s documented); plaintext/no-auth Kafka & Redis infra (demo scope) |

# 2. EXECUTIVE SUMMARY

**Project name:** Distributed Job Scheduling & Task Execution Platform.

**Category:** Backend-heavy full-stack distributed job-processing system (job scheduler + task executor + REST API + observability), with a thin React admin/user UI.

**Primary problem:** Applications need to run background work (reports, cleanups, notifications) asynchronously, reliably, and observably — without blocking request threads, without losing jobs on restart, without double-executing them under concurrency, and with bounded resources. Doing this naively with "fire a thread per request" or "cron + sleep" fails under load, crashes, and races.

**Why the problem matters:** Background execution is where production systems lose data and money: duplicate side effects, silently swallowed failures, unbounded thread/connection consumption, no retry strategy, and no way to see what happened. This project exists to demonstrate the correct engineering for each of those failure classes in one coherent system.

**Target use case:** A multi-tenant platform where authenticated users submit jobs (e.g., "generate report", "send email", "cleanup data"), watch their lifecycle, retry failed work, and where an administrator can recover permanently-dead jobs — a realistic model of internal task platforms.

**High-level solution:** PostgreSQL is the single source of truth for job state. A `@Scheduled` poller admits due jobs (CREATED / due SCHEDULED / due RETRYING) into QUEUED state. A bounded `ThreadPoolExecutor` worker pool dispatches QUEUED jobs **highest-priority-first** and *claims* each job via an **atomic conditional SQL UPDATE** (`QUEUED→RUNNING`), so exactly one worker wins even under contention. The handler runs with `future.get(timeout)`: success → atomic `RUNNING→SUCCESS`, failure/timeout → atomic `RUNNING→FAILED` followed by automatic retry with exponential backoff (`RETRYING` + backoff deadline) or `DEAD` when retries are exhausted. Admins recover DEAD jobs back to QUEUED. Every state change emits a Kafka lifecycle event that an audit consumer persists idempotently (unique `eventId`) into PostgreSQL. Job creation is idempotent per `Idempotency-Key` (owner-scoped, unique DB constraint, race-resolved via constraint violation → re-lookup). Redis provides per-user sliding-window rate limiting via an atomic Lua script (fail-open by default). Micrometer/Actuator expose counters, gauges, and an execution-duration timer to Prometheus, visualized in a provisioned Grafana dashboard. JWT (HS256) secures the API; ownership is enforced per record with 404 masking; registration can never mint ADMIN accounts.

**Main architectural style:** Modular monolith with asynchronous internal pipeline (poller → queue → worker pool) + event spine (Kafka → audit). Not microservices; "distributed" refers to the concurrency/distribution *concerns* handled (competing workers, race prevention, at-least-once events), not to a multi-node deployment — the design explicitly documents single-instance limitations (§39/§40).

**Backend stack:** Java 17 · Spring Boot 3.2.5 · Spring Web MVC · Spring Data JPA/Hibernate · PostgreSQL 16 · Spring Security + JJWT 0.12.5 (HS256) · Spring Data Redis (Lettuce) · Spring Kafka 3.1.4 / kafka-clients 3.6.2 (KRaft broker) · Actuator + Micrometer Prometheus registry · springdoc-openapi (Swagger UI) · Maven.

**Frontend stack:** React 18 · Vite 5 · react-router-dom 6 · Tailwind CSS 3 · dev-proxy `/api → :8080`.

**Infrastructure:** Docker Compose — app (pre-built jar on JRE-17-alpine), postgres:16-alpine, redis:7-alpine, confluentinc/cp-kafka:7.6.0 (KRaft, no ZooKeeper), prom/prometheus:v2.51.0, grafana/grafana:10.4.0; 5 named volumes; healthchecks + `depends_on: condition: service_healthy`.

**Reliability mechanisms:** guarded 9-state state machine; atomic conditional-update claiming and completion; retry with exponential backoff (1s base, 2×, 30 s cap); cooperative timeout detection; retries-exhausted → DEAD; admin recovery; DB-unique idempotency with owner scoping; Kafka events persisted idempotently; `CallerRunsPolicy` backpressure; graceful shutdown.

**Security mechanisms:** BCrypt hashes; HS256 JWT with 24 h expiry; stateless filter chain; role-based URL rules + `@PreAuthorize`; ownership → 404 (no existence leak); registration always USER (anti-privilege-escalation, regression-tested); 10 000-char payload cap; bean validation; global exception handler with generic 500s; no command execution anywhere (handlers are simulated).

**Observability:** 6 job counters, rate-limit rejection counter, execution-duration timer (p50/p95/p99), active-workers and queue-depth gauges, `@Timed` API timers (via registered `TimedAspect`) → `/actuator/prometheus` → Prometheus (15 s scrape) → Grafana "Job Platform Overview" (10 panels, provisioned).

**Testing:** 128 automated tests in 8 classes (unit + Spring integration + concurrency + security + Kafka-consumer-logic), all green per Surefire reports committed in `target/`; plus a stdlib-only end-to-end verification script for the live Docker stack.

**Current completion status:** Implementation-complete per README; every claimed feature is present in code; 128/128 tests pass (Surefire evidence); Docker-stack runtime verification is *documented* in README (scenarios A–K, 15/15) and the script that produced it is shipped, but the raw runtime logs themselves are not in the tree (see §29 for the strict implemented/tested/runtime-verified matrix).

**Intentional limitations (documented by the project itself):** at-least-once execution (not exactly-once); cooperative-only timeout termination; single-instance scheduler (no distributed lock); in-memory dispatch queue (DB is the recovery source); simulated handlers only; no Kafka/Redis auth/TLS; Grafana dashboard functional rather than polished.

**Project in one sentence:** *A PostgreSQL-backed job scheduling and execution platform in Spring Boot where a scheduler, a bounded worker pool, atomic conditional-update claiming, retry with exponential backoff, timeouts, idempotent creation, JWT security, Redis rate limiting, Kafka audit events, and Prometheus/Grafana observability together deliver reliable multi-user background-job processing.*

**Project in five sentences:** Users create jobs through a validated, JWT-secured, rate-limited REST API; jobs are stored in PostgreSQL and move through a guarded nine-state machine. A `@Scheduled` poller admits due jobs into QUEUED state, ordered by priority. A bounded worker pool claims each job with an atomic conditional UPDATE so no two workers can ever run the same job simultaneously, then executes the mapped handler under a per-job timeout. Failures trigger automatic retries with exponential backoff until either success or the DEAD state, from which only an admin can recover a job. Every transition is published to Kafka, persisted idempotently into an audit table, and measured via Micrometer→Prometheus→Grafana.

**Project in interview-ready explanation:** "It's a distributed job scheduling and task execution platform built with Spring Boot. PostgreSQL is the source of truth for job state, and all concurrency correctness lives in the database: workers claim jobs with an atomic conditional UPDATE from QUEUED to RUNNING, so under contention exactly one worker wins — I proved that with a 10-thread race test. A Spring `@Scheduled` poller picks up due jobs and a bounded ThreadPoolExecutor runs them priority-first with per-job timeout via CompletableFuture. Failures move the job to RETRYING with an exponential backoff deadline computed as min(1s·2^n, 30s), and the scheduler re-queues it when the deadline passes; exhausted retries go to a terminal DEAD state that only admins can recover. Job creation is idempotent — the Idempotency-Key header plus a unique constraint, with concurrent duplicates resolved through the DataIntegrityViolationException path, and keys are owner-scoped so one user can't probe another's keys. Every state change is published to Kafka as a lifecycle event and an audit consumer persists them idempotently by eventId into an audit table — at-least-once delivery, duplicate-safe consumption. Redis handles per-user sliding-window rate limiting with an atomic Lua script and a fail-open policy, and the whole thing is observable through Micrometer, Prometheus, and a provisioned Grafana dashboard. It's secured with JWT, BCrypt, and ownership checks that return 404 instead of 403 to avoid leaking existence."

# 3. WHAT THE PROJECT ACTUALLY DOES (END-TO-END, IN PLAIN LANGUAGE)

**Realistic example:** Alice (`user`) logs in and submits "Generate monthly report" with `type=REPORT`, `priority=HIGH`, `timeoutSeconds=300`, and header `Idempotency-Key: report-may-2026`.

The full journey — every arrow explained:

1. **User → API.** Alice's browser (React) sends `POST /api/jobs` with `Authorization: Bearer <JWT>` and `Idempotency-Key` header. In dev, the request goes through Vite's proxy (`localhost:5173/api → localhost:8080/api`).
2. **→ Security.** `JwtAuthenticationFilter` (a `OncePerRequestFilter` registered before Spring's username/password filter) extracts the Bearer token, verifies the HS256 signature via `JwtTokenProvider.validateToken`, loads the user via `CustomUserDetailsService` (role → `ROLE_USER`), and populates `SecurityContext`. Invalid/missing token → request proceeds unauthenticated → later blocked with 401 JSON by `SecurityConfig`'s `authenticationEntryPoint`.
3. **→ Rate limiting.** `JobController.createJob` first calls `checkRateLimit(authentication)`: `RateLimitService` runs one atomic Lua script against Redis with keys `rate_limit:{username}:{minuteIndex}` and `rate_limit:{username}:{minuteIndex-1}`, weighting the previous bucket by elapsed window time (sliding-window counter). Over limit → counter `rate_limit.rejections` incremented, `RateLimitException` thrown → `GlobalExceptionHandler` returns 429 with `Retry-After: 60` and `X-RateLimit-Remaining: 0`. Under limit → response will carry `X-RateLimit-Limit` / `X-RateLimit-Remaining` headers.
4. **→ Validation.** `@Valid @RequestBody CreateJobRequest` enforces: name 1–255 chars, type is a real `JobType` enum, payload ≤ 10 000 chars, maxRetries 1–10, timeoutSeconds 1–3600. Malformed JSON/unknown enum → 400 via `HttpMessageNotReadableException` handler.
5. **→ JobService.** `JobController.createJob` copies the header into the request, then calls `jobService.createJob(request, username)`. `JobService.createJob` first checks `handlerRegistry.hasHandler(type)` (unknown type → 400), then routes to `handleIdempotency` because a key is present.
6. **→ Idempotency check.** `idempotencyRepository.findByIdempotencyKey("report-may-2026")`. If a record exists **and belongs to Alice** → her existing job is returned unchanged (original payload wins). If it belongs to someone else → neutral `DuplicateJobException` → 409 with no information about the key. If absent → proceed to insert.
7. **→ PostgreSQL.** `jobRepository.save(job)` inserts a `jobs` row: status `QUEUED` (immediate) or `SCHEDULED` (future `scheduledAt`), priority HIGH (numeric 1), retryCount 0, maxRetries 3, timeoutSeconds 300, `version=0`, unique `idempotencyKey`. Then `idempotencyRepository.save(new IdempotencyRecord(key, jobId, alice))`. If a concurrent duplicate insert loses the race, the unique constraint raises `DataIntegrityViolationException`, which is caught and resolved by re-reading the winner's row — both concurrent callers get the **same** job id.
8. **→ Events.** `JobEventPublisher.publishEvent(JOB_CREATED, jobId, owner)` (and `JOB_QUEUED` if immediate) builds a `JobEvent` with a fresh `eventId` UUID, serializes to JSON, and `KafkaTemplate.send("job-lifecycle-events", jobId, json)` fires asynchronously; failures are logged, never propagated.
9. **→ Metrics.** `jobCreatedCounter` (`jobs.created` → Prometheus `jobs_created_total`) increments.
10. **→ Scheduler.** Every scheduler tick, `JobScheduler.scheduleDueJobs()` runs `jobService.getDueJobs(50)` — a JPQL query selecting `CREATED` jobs, `SCHEDULED` jobs whose `scheduledAt ≤ now`, and `RETRYING` jobs whose backoff deadline passed, `ORDER BY priority ASC, scheduledAt ASC NULLS LAST`. For each: `jobService.scheduleJob(job)` validates `SCHEDULED→QUEUED` in the state machine and saves; then `workerPool.submit(job)`. The loop then re-queries `findQueuedJobsForDispatch(50)` and submits those too (covers pre-existing QUEUED jobs), updating the `jobs.queue.depth` gauge. *(Note: due to the interval-unit discrepancy, this loop currently runs every ~5 ms; see §14/§56.)*
11. **→ Queue/dispatch.** `WorkerPool.submit` de-dupes per-instance via `submittedJobIds` (a `ConcurrentHashMap.newKeySet()`), then `executor.submit(task)` onto the `ThreadPoolExecutor(5 threads, LinkedBlockingQueue(100), CallerRunsPolicy)`. Queue full → the scheduler thread runs the task itself (backpressure). Ordering between SQL priority selection and executor FIFO is explained in §15.
12. **→ Atomic claim.** The worker task calls `jobService.claimJob(jobId)` → `jobRepository.claimJob`: `UPDATE jobs SET status='RUNNING', started_at=:now WHERE id=:jobId AND status='QUEUED'` in its **own short transaction**. Returns 1 = won (JOB_STARTED event published); 0 = someone else claimed → worker exits silently. This is the duplicate-execution guard.
13. **→ Execution.** `jobService.executeJob(job)` (deliberately **not** `@Transactional`): creates a `job_attempts` row (`STARTED`, attemptNumber = retryCount+1), gets `ReportHandler` from the registry, and runs `CompletableFuture.supplyAsync(() -> handler.execute(jobId, payload))`. The handler simulates 5 s of work. The worker thread blocks in `future.get(300, SECONDS)`.
14. **→ Outcome.** Handler returns JSON → `completeJob`: attempt → `COMPLETED`, a `job_results` row saved, `markJobSuccessIfRunning` atomic update (only wins if still RUNNING), `JOB_SUCCEEDED` event, `jobs.completed` counter, execution duration recorded into the `jobs.execution.duration` timer (p50/p95/p99). If the handler had thrown or timed out → `failJobAndRetry`/`handleTimeout`: attempt `FAILED`/`TIMED_OUT` with error class/message, a failure `job_results` row, atomic `markJobFailedIfRunning`, `JOB_FAILED` event, then `handleRetryableFailure`.
15. **→ Retry/DEAD decision.** `handleRetryableFailure` (job now FAILED): if `retryCount >= maxRetries` → validate `FAILED→DEAD`, save DEAD, publish `JOB_DEAD`, increment `jobs.dead`. Else → backoff = `min(1000·2^retryCount, 30000)` ms; validate `FAILED→RETRYING`, set retryCount+1 and `scheduledAt = now + backoff`, publish `JOB_RETRYING`, increment `jobs.retried`. The scheduler later flips `RETRYING→QUEUED` when the deadline passes.
16. **→ Audit.** `JobEventConsumer` (group `job-platform-audit-consumer`) receives each event JSON, skips if `existsByEventId`, else inserts a `job_audit_events` row (eventId unique ⇒ duplicates from Kafka at-least-once redelivery are harmless; concurrent duplicates die on the constraint and are ignored). Consumer failures affect only the audit trail, never job state.
17. **→ Metrics → Prometheus → Grafana.** Micrometer counters/gauges/timers are exposed at `/actuator/prometheus`; Prometheus scrapes every 15 s; Grafana's provisioned "Job Platform Overview" dashboard renders jobs created/succeeded/failed/dead, queue depth, active workers, lifecycle rates, execution duration (mean + p95/p99), rate-limit rejections, and `@Timed` request rate.
18. **→ User sees result.** Alice polls `GET /api/jobs/{id}` (owner-checked) → sees `SUCCESS`, `startedAt`/`completedAt`, retries 0/3; `GET /api/jobs/{id}/result` returns the report JSON; `GET /api/jobs/{id}/attempts` shows the attempt history.

| # | Problem | Naive solution | Why naive fails | This project's solution (with code anchors) | Why better | Tradeoff |
|---|---|---|---|---|---|---|
| 1 | **Scheduling** delayed work | In-memory timer per request | Timers die on restart; unbounded timer count | `jobs.scheduledAt` column + `findDueJobs` poller (`JobRepository.findDueJobs`, `JobService.getDueJobs`) | Durable; jobs survive restarts; backoff reuses the same mechanism | ±poll-interval precision; DB polling cost |
| 2 | **Background execution** | Execute inline in the HTTP thread | Ties up request threads; timeouts kill client connection; no lifecycle | Scheduler→queue→worker pipeline; API only persists state | API stays fast; execution is observable/retryable | Extra moving parts (poller, pool) |
| 3 | **Concurrent execution** | One thread per job, unbounded | Thread explosion under load; OOM | Bounded `ThreadPoolExecutor(5,5,LinkedBlockingQueue(100))` (`WorkerPool`) | Predictable resource usage; backpressure via CallerRunsPolicy | Throughput capped at pool size; queued jobs wait |
| 4 | **Bounded resources** | `newCachedThreadPool` | Unbounded threads; DB connection exhaustion | Fixed pool + bounded queue + rejection policy | Fails gracefully under overload (caller runs) | Long jobs can starve the queue (5 workers) |
| 5 | **Race conditions** on claiming | Read status, check ==QUEUED, then write RUNNING (read-then-write) | Two workers both read QUEUED and both proceed → double execution | Atomic conditional UPDATE `... | 6 | **Duplicate execution** | In-memory locks / synchronized | Useless across restarts/multi-instance; memory leaks | DB is the arbiter: claim UPDATE + per-instance dedup set + atomic success/fail guards (`markJobSuccessIfRunning`/`markJobFailedIfRunning`) | Correct under contention and crash-restart re-dispatch | Not exactly-once (at-least-once; documented §39) |

```
   ▼                      │
QUEUED ◄──────────────────┼──────────────────────────────┐
   │  (claimJob:          │                              │
   │   atomic UPDATE)     │ RETRYING ──► (scheduler:     │
   ▼                      │   ▲          backoff passed) │
RUNNING ──────────────────┘   │                          │
   │    │    │                │ FAILED (atomic UPDATE;   │
   │    │    └─► RETRYING ────┘  then handleRetryable- │
   │    │         (retryCount+1,  Failure branches)    │
   │    │          scheduledAt=now+backoff)            │
   │    └─► FAILED ──► DEAD (retryCount ≥ maxRetries) ──┘
   │              (DEAD is terminal; only validateRecovery → QUEUED:
   ▼               admin /recover or owner retry of DEAD, retryCount reset)
SUCCESS (terminal)
```

# 6. ARCHITECTURAL DECISION RECORD (ADR)

Each record: What / Why / Problem solved / Where implemented / Why not simpler / Tradeoffs / Limitations.

### ADR-01 Java 17
- **What:** Language/runtime version 17 (`pom.xml` `<java.version>`, `eclipse-temurin:17-jre-alpine` runtime image).
- **Why:** LTS baseline required by Spring Boot 3.x; records/text blocks not used but modern switch/`Set.of`/`EnumMap` idioms appear.
- **Where:** `pom.xml`, `Dockerfile`.
- **Why not Java 8/11:** Spring Boot 3 requires 17.
- **Tradeoffs/Limitations:** none project-specific.

### ADR-02 Spring Boot 3.2.5 (monolith)
- **What:** Single Spring Boot application containing API, scheduling, workers, consumers.
- **Why:** One deployable; all correctness flows through one DB; operational simplicity for a demonstration-scale platform.
- **Where:** `JobPlatformApplication` (`@SpringBootApplication @EnableScheduling`), `pom.xml` parent.
- **Why not microservices:** Cross-service correctness (atomic claim) would need distributed coordination; a monolith with DB-mediated concurrency achieves the goals with far less complexity.
- **Tradeoffs:** Cannot scale scheduler/worker tier independently. **Limitation:** single-instance only (dedup set is per-JVM; scheduler has no leader election) — documented in README limitations.

### ADR-03 Spring Data JPA + Hibernate on PostgreSQL
- **What:** JPA entities with Hibernate-generated schema (`ddl-auto=update`), derived queries + JPQL for the hot paths.
- **Why:** Type-safe persistence, fast development; PostgreSQL provides row-level locking that the whole concurrency design depends on.
- **Where:** 6 entities; `JobRepository` (`findDueJobs`, `claimJob`, `markJobSuccessIfRunning`, `markJobFailedIfRunning`, `findQueuedJobsForDispatch`).
- **Why not JdbcTemplate/raw SQL everywhere:** Derived queries cover CRUD; JPQL retained where atomic conditional semantics matter. **Why not Flyway/Liquibase:** no migration files exist; `ddl-auto=update` is dev-grade (documented limitation — schema drift risk in real deployments).
- **Tradeoffs:** `ddl-auto=update` unsuitable for prod; entity `@Version` present but the correctness-critical paths use conditional UPDATEs rather than optimistic-retry loops.

### ADR-04 PostgreSQL as source of truth + SQL-level atomic claiming
- **What:** `jobs` table owns job state; claim/complete/fail are single conditional UPDATE statements returning affected-row counts.
- **Why:** Correctness under concurrency must not depend on JVM memory; row locks serialize contenders; restarts recover QUEUED/RETRYING work from the DB.
- **Where:** `JobRepository` lines with `@Transactional @Modifying @Query` (claimJob/markJobSuccessIfRunning/markJobFailedIfRunning); indexes `idx_job_status_scheduled(status,scheduledAt)`, `idx_job_owner`, `idx_job_priority`, unique `idx_job_idempotency_key`.
- **Why not in-memory queue or Redis queue:** Both lose state on restart / are not the system of record; DB claiming gives exactly the guarantee needed (one winner).
- **Tradeoffs:** Every claim is a DB write; hot row contention on the same job is negligible since only one worker can win.
- **Limitations:** No SKIP LOCKED-style batch claim (rows are selected then claimed one-by-one); scheduler single-instance.

### ADR-05 In-memory worker pool (ThreadPoolExecutor) instead of durable queue
- **What:** `ThreadPoolExecutor(core=max=5, keepAlive 60s, LinkedBlockingQueue(100), custom "job-worker-N" factory, CallerRunsPolicy)`, `allowCoreThreadTimeOut(true)`.
- **Why:** Simple bounded parallelism with backpressure; the DB already provides durability — the pool is only a dispatch buffer.
- **Where:** `WorkerPool` constructor; `submit()` with `submittedJobIds` dedup; `@PreDestroy shutdown()` (await 30 s → `shutdownNow`).
- **Why not a message-broker queue:** Kafka-as-queue would add delivery complexity without removing the DB claim step; the README explicitly designates Kafka as event bus only.
- **Tradeoffs:** On crash, submitted-but-not-claimed work is not lost (jobs stay QUEUED in DB and are re-discovered by the scheduler) — but an in-flight RUNNING job at crash time remains RUNNING forever (no lease/visibility-timeout mechanism; see §34 crash analysis).
- **Limitations:** Queue capacity 100 then CallerRunsPolicy makes the scheduler thread execute jobs synchronously (intentional backpressure, can slow the polling loop).

### ADR-06 Spring `@Scheduled` polling instead of cron/quartz/distributed scheduler
- **What:** `@Scheduled(fixedDelayString = "${app.scheduler.interval-seconds:5}", initialDelay = 5000)` on `JobScheduler.scheduleDueJobs()`.
- **Why:** No extra dependency; fixed-delay prevents overlap of a slow cycle with the next.
- **Where:** `JobScheduler` (annotation at method), interval in `application.properties` `app.scheduler.interval-seconds=5`, batch size `app.scheduler.batch-size=50`.
- **⚠ DOCUMENTATION DISCREPANCY (important):** Spring interprets a plain number in `fixedDelayString` as **milliseconds**. There is no `application-docker.properties` and `SPRING_PROFILES_ACTIVE=docker` (compose) selects no existing profile file. Therefore the property resolves to `5` → the loop runs **every 5 milliseconds** (~200 due-queries + ~200 dispatch-queries per second against PostgreSQL), not every 5 seconds as the property name, README ("Scheduler Tolerance ±5 second", "interval 5s" in e2e comments) imply. Functionally the system still behaves correctly (polling more often is safe; `fixedDelay` prevents overlap; dedup set + atomic claim neutralize double dispatch), but the DB polling load is ~200× the documented intent and precision is ±5 ms, not ±5 s. **Classification: BUG (unit mismatch), not a crash risk; documented-only, NOT fixed in this audit.** See §14 and §56.
- **Tradeoffs:** Polling is simple but wastes queries; a distributed deployment would need leader election or partitioned scanning. **Limitations:** precision tied to interval; single instance.

### ADR-07 JWT (JJWT 0.12.5, HS256) + stateless Spring Security
- **What:** Bearer-token auth; 24 h expiry; claims = sub/iat/exp only (no roles in token — role is loaded from DB per request).
- **Why:** Stateless horizontal scaling-friendly auth for an SPA; simple.
- **Where:** `JwtTokenProvider` (key = `Keys.hmacShaKeyFor(Base64.decode(app.jwt.secret))`; `generateToken` ×2, `getUsernameFromToken`, `validateToken`), `JwtAuthenticationFilter`, `SecurityConfig` (filter placement, entry point/access-denied JSON), `CustomUserDetailsService` (`ROLE_<role>` authority).
- **Why not sessions/OAuth2:** Sessions need sticky state; OAuth2 needs an external IdP — out of scope for this platform.
- **Tradeoffs:** No refresh tokens, no revocation, secret is a single shared symmetric key. **Limitations:** JWT secret default is a documented development value; role changes take effect on next request (DB read), token itself carries no role claim (good for revocation semantics).

### ADR-08 BCrypt password hashing
- **What:** `BCryptPasswordEncoder` bean used in registration and `DataInitializer`.
- **Why:** Standard adaptive hash; salted per user.
- **Where:** `SecurityConfig.passwordEncoder()`, `AuthController.register`, `DataInitializer.run`.
- **Why not SHA-256:** unsalted/fast hashes are inappropriate for passwords.
- **Tradeoffs:** BCrypt strength default (10) not tuned/configurable.

### ADR-09 Redis for rate limiting ONLY (Lua sliding-window counter)
- **What:** Per-user request limiting: 100 req/min default; atomic Lua script; two adjacent minute buckets; fail-open configurable.
- **Why:** Atomicity across check+increment requires a single-server operation (Lua); sliding window avoids the classic 2× boundary burst of fixed windows.
- **Where:** `RateLimitService` (script constant, `checkRateLimit`, `RateLimitResult`), applied in `JobController.checkRateLimit` (POST /api/jobs only); headers `X-RateLimit-Limit/Remaining`, 429 via `GlobalExceptionHandler` (`Retry-After: 60`).
- **Why not in-app counters / Guava RateLimiter:** Not shared across instances, not atomic under concurrency.
- **Tradeoffs:** Adds Redis dependency on the write path; fail-open keeps availability when Redis is down (documented decision). **CRITICAL SCOPING FACT:** Redis stores **nothing** about jobs — it is NOT the source of truth for job state; keys `rate_limit:{userId}:{windowIndex}` with TTL 120 s are the only data written.

### ADR-10 Kafka for lifecycle events + idempotent audit consumer (NOT the task queue)
- **What:** Topic `job-lifecycle-events` (3 partitions, RF 1), string-JSON events keyed by jobId; consumer group `job-platform-audit-consumer` persists to `job_audit_events` with unique `eventId` dedup.
- **Why:** Decouples audit/notifications from the execution path; per-key partitioning gives per-job ordering; at-least-once + idempotent consumer = duplicate-safe audit trail.
- **Where:** `KafkaConfig` (NewTopic), `JobEventPublisher` (async send, failures logged & swallowed), `JobEventConsumer` (`@KafkaListener`, `@Transactional`, DIVE tolerance), `JobAuditEvent` entity.
- **Why not Kafka as the work queue:** Task execution requires per-job state transitions (QUEUED/RUNNING/retry/dead) and exactly-one-winner semantics; the DB claim already provides that, and a broker would add re-delivery ambiguity for *execution* (at-least-once consumption ⇒ possible duplicate executions). The design keeps Kafka strictly on the event/audit side. (README: "Kafka is Async: event publishing failure does not affect job state".)
- **Tradeoffs:** Publishing is best-effort (no outbox) ⇒ events can be lost on process crash between DB commit and Kafka send; audit trail may have gaps (documented).
- **Limitations:** Single broker RF 1 (dev); no consumer retry/DLQ — malformed messages are dropped after logging; producer has default acks (no explicit durability tuning in code).

### ADR-11 Micrometer + Actuator + Prometheus + Grafana
- **What:** Code-level meters + `@Timed` aspect; scrape endpoint; provisioned dashboard.
- **Why:** Standard Spring metrics stack; percentiles for execution duration; zero-app-code scraping infrastructure.
- **Where:** `MetricsConfig` (incl. `TimedAspect` bean — added after the Phase-3 audit found `@Timed` was dead without it), `application.properties` actuator exposure, `docker/prometheus/prometheus.yml`, `docker/grafana/**`.
- **Why not logs-only:** no aggregation/percentiles.
- **Tradeoffs:** p50/95/99 are client-side (non-aggregable) histograms; no alertmanager. **Limitations:** panel 10 queries `by (status)` but the `api_jobs_create_seconds` metric carries no `status` tag (TimedAspect default tags only) — grouping is effectively inert (§25).

### ADR-12 React 18 + Vite + Tailwind SPA with dev proxy
- **What:** Thin management UI; token in `localStorage`; all API calls via `utils/api.js` wrapper.
- **Why:** Fast dev iteration (Vite), minimal styling effort, no SSR need.
- **Where:** `frontend/*` (detailed in §27).
- **Why not SSR/Next:** No SEO requirements; API-first design.
- **Tradeoffs:** `localStorage` token storage is XSS-exposed (standard SPA tradeoff, documented in §38); `dist/` build is committed; no admin jobs page in UI despite `jobsApi.adminList` existing (API-only feature).

### ADR-13 Docker Compose with KRaft Kafka (no ZooKeeper) and health-gated startup
- **What:** 6 services; app healthcheck via curl on `/actuator/health`; kafka healthcheck via `kafka-topics --list`; `depends_on: condition: service_healthy`.
- **Why:** Deterministic startup ordering; KRaft removes ZooKeeper operational burden.
- **Where:** `docker-compose.yml` (full service table §26); app image requires the **pre-built** jar (`mvn package -DskipTests` before `docker compose up --build`) per Dockerfile comment (Maven-in-container needs Maven Central network access).
- **Tradeoffs:** Two-step build documented in README; dev credentials committed (labeled DEVELOPMENT ONLY).

### ADR-14 H2 in-memory DB for tests + Mockito-mocked Redis/Kafka
- **What:** `src/test/resources/application.properties` (H2, create-drop, redis/kafka health disabled, port 0); `TestConfig` provides `@Primary` Mockito mocks for `StringRedisTemplate` and `KafkaTemplate`.
- **Why:** Fast, hermetic integration tests without infrastructure.
- **Where:** test tree (§28).
- **Tradeoffs:** H2 ≠ PostgreSQL semantics for locking; however the atomic-claim correctness tests still exercise real conditional-update SQL against H2, and the *real* PostgreSQL path was runtime-verified (README Phase-3 + e2e script).

### `JobPlatformApplication` — `src/main/java/.../JobPlatformApplication.java`

- **Members:** `main(String[])` only.

### `config.SecurityConfig`
- **Responsibility:** the entire HTTP security posture.
- **Key members:** `securityFilterChain(HttpSecurity)` — CSRF disabled, `SessionCreationPolicy.STATELESS`, URL rules (public: `/api/auth/**`, `/actuator/health`, `/actuator/prometheus`, swagger, h2-console, static assets; ADMIN: `POST /api/jobs/*/recover`, `GET /api/jobs/admin/**`; everything else authenticated), custom JSON `authenticationEntryPoint` (401) and `accessDeniedHandler` (403), `frameOptions` disabled, `addFilterBefore(jwtAuthenticationFilter, UsernamePasswordAuthenticationFilter.class)`; `passwordEncoder()` → BCrypt; `authenticationManager()` from `AuthenticationConfiguration`.

### `config.JwtAuthenticationFilter` (in `security/`)
- **Responsibility:** convert `Authorization: Bearer` into an `Authentication` in `SecurityContextHolder`.

Any exception → log at debug, continue **unauthenticated** (never blocks the chain; authorization then rejects).
- **Concurrency:** stateless per request; no session is created.
- **Interview:** the exact answer to "how does a request become authenticated?"

### `security.JwtTokenProvider`
- **Responsibility:** issue and verify HS256 JWTs.
- **Fields:** `SecretKey key` (from Base64-decoded `app.jwt.secret`), `long jwtExpirationMs` (86 400 000).
- **Methods:** `generateToken(Authentication)` (uses principal's username), `generateToken(String username)` (used by register), `getUsernameFromToken` (parse → payload → subject), `validateToken` (parse; `JwtException | IllegalArgumentException` → false + debug log).
- **Claims:** `sub` (username), `iat`, `exp`. **No role claim** — role is resolved from DB on every request via `CustomUserDetailsService` (means role changes take effect immediately; token forgery can't elevate roles).
- **Security:** signature verification is the only trust boundary; dev default secret is flagged in §32/§38.
- **Interview:** token contents, expiry, and why roles aren't in the token.

### `security.CustomUserDetailsService`
- **Responsibility:** `User` entity → Spring `UserDetails` with `SimpleGrantedAuthority("ROLE_" + role)`.
- **Called by:** `JwtAuthenticationFilter` (every authenticated request) and `AuthenticationManager` (login).
- **Note:** login uses the DaoAuthenticationProvider path — `authenticate(UsernamePasswordAuthenticationToken)` in `AuthController.login` triggers `loadUserByUsername` + BCrypt `matches` internally.

## CODE-001 — Job creation entry (`JobService.createJob` + `doCreateJob`)

```java
public JobResponse createJob(CreateJobRequest request, String ownerId) {
    if (!handlerRegistry.hasHandler(request.getType())) {
        throw new IllegalArgumentException("No handler registered for job type: " + request.getType());
    }

    if (request.getIdempotencyKey() != null && !request.getIdempotencyKey().isBlank()) {
        return handleIdempotency(request, ownerId);
    }

    return doCreateJob(request, ownerId);
}

private JobResponse doCreateJob(CreateJobRequest request, String ownerId) {
    Job job = new Job(ownerId, request.getName(), request.getType(), request.getPriority(), request.getPayload());
    job.setMaxRetries(request.getMaxRetries());
    job.setTimeoutSeconds(request.getTimeoutSeconds());
    job.setIdempotencyKey(request.getIdempotencyKey());

    if (request.getScheduledAt() != null && request.getScheduledAt().isAfter(Instant.now())) {
        job.setScheduledAt(request.getScheduledAt());
        stateMachine.validateTransition(JobStatus.CREATED, JobStatus.SCHEDULED);
        job.setStatus(JobStatus.SCHEDULED);
    } else {
        stateMachine.validateTransition(JobStatus.CREATED, JobStatus.QUEUED);
        job.setStatus(JobStatus.QUEUED);
        if (request.getScheduledAt() != null) {
            job.setScheduledAt(request.getScheduledAt());
        }
    }

    job = jobRepository.save(job);

    eventPublisher.publishEvent(JobEventType.JOB_CREATED, job.getId(), ownerId);
    if (job.getStatus() == JobStatus.QUEUED) {
        eventPublisher.publishEvent(JobEventType.JOB_QUEUED, job.getId(), ownerId);
    }

    jobCreatedCounter.increment();
    log.info("Job created: {} (type={}, priority={}, status={})", job.getId(), job.getType(), job.getPriority(), job.getStatus());

    return toResponse(job);
}
```

**Line by line:**
- `hasHandler` check → fail fast with 400 (via `IllegalArgumentException` handler) before any DB work; prevents creating jobs that could never execute.
- key-present check → route to the idempotent path (CODE-003).
- `new Job(...)` → entity with defaults: status CREATED, priority from request, retryCount 0, maxRetries/timeout overridden from request, `createdAt/updatedAt = now`.
- Future `scheduledAt` → validate `CREATED→SCHEDULED` then set status SCHEDULED (job waits for the scheduler to see `scheduledAt ≤ now`).
- Otherwise → validate `CREATED→QUEUED`, set QUEUED (immediately dispatchable). A *past* `scheduledAt` lands here and is stored as informational.
- `save` → INSERT; Hibernate assigns the UUID and `version=0`.
- Events: JOB_CREATED always; JOB_QUEUED additionally when immediately queueable (a SCHEDULED job's JOB_QUEUED fires later from `scheduleJob`).
- Counter + log; return DTO.

**Why:** the state machine is consulted *even on insert* so every persisted status is a legal product of a legal transition from CREATED. The class Javadoc explains the deliberate absence of `@Transactional` here: each repository call runs in its own transaction so an idempotency-race `DataIntegrityViolationException` doesn't poison a surrounding transaction.

## CODE-003 — Idempotency with owner scoping and race resolution (`JobService.handleIdempotency`)

```java
private JobResponse handleIdempotency(CreateJobRequest request, String ownerId) {
    String key = request.getIdempotencyKey();

    IdempotencyRecord existing = idempotencyRepository.findByIdempotencyKey(key).orElse(null);
    if (existing != null) {
        // SECURITY: idempotency keys are scoped to their owner. A key recorded for a
        // different user must not reveal that user's job (existence oracle / data leak).
        if (!existing.getOwnerId().equals(ownerId)) {
            log.warn("Idempotency key {} belongs to a different owner; rejecting with 409", key);
            throw new DuplicateJobException("Idempotency key conflict");
        }
        log.info("Duplicate idempotency key detected: {}, returning existing job: {}", key, existing.getJobId());
        Job existingJob = jobRepository.findById(existing.getJobId())
            .orElseThrow(() -> new JobNotFoundException(existing.getJobId()));
        return toResponse(existingJob);
    }

    try {
        Job job = new Job(ownerId, request.getName(), request.getType(), request.getPriority(), request.getPayload());
        job.setMaxRetries(request.getMaxRetries());
        job.setTimeoutSeconds(request.getTimeoutSeconds());
        job.setIdempotencyKey(key);

        if (request.getScheduledAt() != null && request.getScheduledAt().isAfter(Instant.now())) {
            job.setScheduledAt(request.getScheduledAt());
            job.setStatus(JobStatus.SCHEDULED);
        } else {
            job.setStatus(JobStatus.QUEUED);
            if (request.getScheduledAt() != null) {
                job.setScheduledAt(request.getScheduledAt());
            }
        }

        job = jobRepository.save(job);

        IdempotencyRecord record = new IdempotencyRecord(key, job.getId(), ownerId);
        idempotencyRepository.save(record);

        eventPublisher.publishEvent(JobEventType.JOB_CREATED, job.getId(), ownerId);
        if (job.getStatus() == JobStatus.QUEUED) {
            eventPublisher.publishEvent(JobEventType.JOB_QUEUED, job.getId(), ownerId);
        }

        jobCreatedCounter.increment();
        return toResponse(job);

    } catch (DataIntegrityViolationException e) {
        log.info("Concurrent idempotency race for key {}, resolving via lookup", key);
        Job existingJob = jobRepository.findByIdempotencyKey(key).orElse(null);
        if (existingJob != null) {
            // SECURITY: same ownership rule as the pre-insert lookup
            if (!existingJob.getOwnerId().equals(ownerId)) {
                log.warn("Idempotency key {} concurrently claimed by a different owner; rejecting with 409", key);
                throw new DuplicateJobException("Idempotency key conflict");
            }
            return toResponse(existingJob);
        }
        throw new RuntimeException("Concurrent idempotency conflict: key=" + key, e);
    }
}
```

**Flow:** (1) pre-check lookup — same owner → return their existing job (idempotent replay, original data wins); different owner → neutral 409 (no existence oracle). (2) Insert job (unique `jobs.idempotencyKey`) then insert the `idempotency_records` row. (3) If a concurrent request won the insert, the unique constraint fires `DataIntegrityViolationException` → re-lookup → same-owner callers converge on the winner's job id; different-owner callers get 409; the impossible "lost race but no row found" case rethrows (→ 500) rather than fabricating a result.
**Why no `@Transactional`:** the class comment states each repository call is its own transaction so the constraint violation doesn't mark an enclosing transaction rollback-only — the fallback lookup must succeed *after* the failed insert.
**Note:** the insert path here skips `stateMachine.validateTransition` (unlike `doCreateJob`) — status assignment is identical, so the transition invariant still holds; this is a minor duplication inconsistency, not a correctness gap (covered in §50).

## CODE-004 — State transition guard (`JobStateMachine`, core excerpt)


## CODE-005 — Scheduler loop (`JobScheduler.scheduleDueJobs`)

```java
@Scheduled(fixedDelayString = "${app.scheduler.interval-seconds:5}", initialDelay = 5000)
public void scheduleDueJobs() {
    try {
        List<Job> dueJobs = jobService.getDueJobs(batchSize);

        int scheduled = 0;
        for (Job job : dueJobs) {
            try {
                jobService.scheduleJob(job);
                workerPool.submit(job);
                scheduled++;
            } catch (Exception e) {
                log.error("Failed to schedule job {}: {}", job.getId(), e.getMessage());
            }
        }

        List<Job> queuedJobs = jobService.getQueuedJobsForDispatch(batchSize);
        for (Job job : queuedJobs) {
            try {
                workerPool.submit(job);
            } catch (Exception e) {
                log.debug("Job {} may already be submitted: {}", job.getId(), e.getMessage());
            }
        }

        queueDepth.set(queuedJobs.size());

    } catch (Exception e) {
        log.error("Error in scheduling loop: {}", e.getMessage());
    }
}
```
**Line by line:** `fixedDelayString` → delay measured **from the end of the previous run** (no overlap); `initialDelay = 5000` ms grace at boot. Step 1 fetches ≤50 due jobs (CREATED / due SCHEDULED / due RETRYING) priority-ordered. Step 2 legalizes each into QUEUED and submits; a single bad job cannot break the batch. Step 3 re-serves QUEUED jobs (restart recovery + retry-path jobs whose submit failed earlier). Step 4 publishes queue-depth for Grafana. Outer catch keeps the timer alive no matter what.
**⚠ Unit discrepancy:** `fixedDelayString` with a plain number is **milliseconds** in Spring → `5` = 5 ms (see §11/§50). The loop is functionally correct but runs ~200×/s.

## CODE-007 — Worker pool construction (`WorkerPool` ctor + `submit`)

```java
this.executor = new ThreadPoolExecutor(
    poolSize,
    poolSize,
    60L, TimeUnit.SECONDS,
    new LinkedBlockingQueue<>(queueCapacity),
    new CustomThreadFactory(),
    new ThreadPoolExecutor.CallerRunsPolicy()
);

        log.debug("Job {} already submitted, skipping", job.getId());
        return;
    }
    submittedJobIds.add(job.getId());
    executor.submit(() -> {
        try {
            activeWorkers.incrementAndGet();
            executeWithClaim(job);
        } finally {
            activeWorkers.decrementAndGet();
            submittedJobIds.remove(job.getId());
        }
    });

```
**Semantics:** core = max = 5 → a fixed-size pool (the `60s` keepAlive only applies because `allowCoreThreadTimeOut(true)` lets idle core threads die); work queue capacity 100; on saturation `CallerRunsPolicy` runs the task **on the scheduler thread** — deliberate backpressure that slows admission instead of dropping work. `submittedJobIds` is a per-instance guard against double-submission within the dedup window (added before submit, removed in `finally` after execution); it is *not* the correctness mechanism — the DB claim is (CODE-009). Gauge wiring: `activeWorkers` is the same `AtomicInteger` bean exposed as `workers.active`.

## CODE-008 — Worker claim-then-execute (`WorkerPool.executeWithClaim`)

```java
private void executeWithClaim(Job job) {
    UUID jobId = job.getId();
    try {
        boolean claimed = jobService.claimJob(jobId);
        if (!claimed) {
            log.debug("Job {} was not claimed (another worker got it)", jobId);
            return;
        }
        jobService.executeJob(job);
    } catch (Exception e) {
        log.error("Unexpected error executing job {}: {}", jobId, e.getMessage());
    }
}
```
**Why:** separates *admission* (job may sit in the executor queue) from *ownership* (claim succeeds immediately before execution). A job can be submitted twice into the pool; only the first claimer proceeds — the loser exits without side effects.

## CODE-009 — Atomic job claim (repository + service)

```java
    int affected = jobRepository.claimJob(jobId, Instant.now());
    if (affected == 1) {
        eventPublisher.publishEvent(JobEventType.JOB_STARTED, jobId, "system");
        log.debug("Job claimed successfully: {}", jobId);
        return true;
    }
    log.debug("Job claim failed (already claimed by another worker): {}", jobId);
    return false;
}
```
**Line by line:** the WHERE clause embeds the expected pre-state (`status='QUEUED'`) — the UPDATE is a compare-and-swap executed by the database under row lock; `@Modifying` marks it as an update; `@Transactional` **on the repository method** gives it its own short transaction (the caller `executeJob` is deliberately non-transactional — see the class Javadoc and §33); the int return is the affected-row count. `affected == 1` ⇒ this worker atomically flipped the state and is the sole owner; `0` ⇒ someone else already won (or the job was cancelled). The JOB_STARTED event publishes with ownerId `"system"` (the claim path doesn't reload the owner — a minor cosmetic inconsistency in the audit trail, noted in §50).
**Race walkthrough (Worker A vs Worker B):** both SELECT the job and see QUEUED (or receive it from the dispatcher). A issues the UPDATE → Postgres locks the row, re-evaluates the WHERE predicate against the current committed value → matches → sets RUNNING → A gets 1. B's UPDATE blocks on the row lock (or arrives after commit) → predicate re-evaluated against RUNNING → no match → B gets 0. **Only one winner, guaranteed by the database, not by JVM locks.**

## CODE-010 — Job execution with timeout (`JobService.executeJob`)

```java
public void executeJob(Job job) {
    UUID jobId = job.getId();
    int attemptNumber = job.getRetryCount() + 1;

    JobAttempt attempt = createAttempt(jobId, attemptNumber);

    try {
        JobHandler handler = handlerRegistry.getHandler(job.getType());

        CompletableFuture<String> future = CompletableFuture.supplyAsync(
            () -> {
                try {
                    return handler.execute(jobId.toString(), job.getPayload());
                } catch (Exception e) {
                    throw new RuntimeException(e);
                }
            }
        );

        String result;
        try {
            result = future.get(job.getTimeoutSeconds(), TimeUnit.SECONDS);
        } catch (TimeoutException e) {
            future.cancel(true);
            handleTimeout(job, attempt);
            return;
        } catch (ExecutionException e) {
            Throwable cause = e.getCause() != null ? e.getCause() : e;
            throw cause instanceof Exception ? (Exception) cause : new RuntimeException(cause);
        }

        completeJob(job, attempt, result);

    } catch (Exception e) {
        failJobAndRetry(job, attempt, e);
    }
}
```
**Line by line:** attempt number = retryCount+1 (first execution = attempt 1). `createAttempt` persists a STARTED row immediately (crash-visible history). The handler runs via `supplyAsync` **on the common ForkJoinPool** (not the worker pool — the worker thread blocks instead); exceptions inside are wrapped so they surface as `ExecutionException`. `future.get(timeoutSeconds, SECONDS)` is the timeout boundary: `TimeoutException` → `cancel(true)` (sends `Thread.interrupt()` to the handler thread — **cooperative only**) → `handleTimeout` → return. `ExecutionException` → unwrap the cause and rethrow so the outer catch treats it like any handler failure. Success → `completeJob`. Any other exception (handler failure, unwrap, registry miss) → `failJobAndRetry`.
**Transaction note (from the Javadoc):** this method is intentionally NOT `@Transactional` — the handler may run up to 3600 s and holding a pooled connection that long would exhaust Hikari under modest concurrency. Every persistence step is its own short transaction; correctness rests on the atomic conditional updates being the last write (§33).

## CODE-012 — Success handling (`JobService.completeJob`)

```java
private void completeJob(Job job, JobAttempt attempt, String resultPayload) {
    attempt.setStatus(AttemptStatus.COMPLETED);
    attempt.setCompletedAt(Instant.now());
    attemptRepository.save(attempt);

    JobResult result = new JobResult(job.getId(), attempt.getId(), true, resultPayload);
    resultRepository.save(result);

    int affected = markJobSuccessIfRunning(job.getId());
    if (affected == 1) {
        eventPublisher.publishEvent(JobEventType.JOB_SUCCEEDED, job.getId(), job.getOwnerId());
        jobCompletedCounter.increment();

        Duration duration = Duration.between(attempt.getStartedAt(), attempt.getCompletedAt());
        jobExecutionTimer.record(duration);

        log.info("Job completed successfully: {} (attempt {})", job.getId(), attempt.getAttemptNumber());
    } else {
        log.debug("Job completion race detected (job already transitioned): {}", job.getId());
    }
}
```
**Order matters:** side-effect-ish records (attempt, result) are written first; the *state decision* (`RUNNING→SUCCESS`, conditional) comes last and gates the event/counter/timer. If a timeout already flipped the job to FAILED, `affected == 0` and the completion silently loses the race — the job's terminal state remains FAILED/RETRYING (a result row for the losing completion may exist, documenting the near-miss; see §32 race #2).

## CODE-013 — Failure handling (`JobService.failJobAndRetry`)

```java
private void failJobAndRetry(Job job, JobAttempt attempt, Exception e) {
    String errorMsg = e.getMessage() != null
        ? e.getMessage().substring(0, Math.min(1000, e.getMessage().length()))
        : "Unknown error";

    attempt.setStatus(AttemptStatus.FAILED);
    attempt.setCompletedAt(Instant.now());
    attempt.setErrorMessage(errorMsg);
    attempt.setErrorClass(e.getClass().getSimpleName());
    attemptRepository.save(attempt);

    JobResult result = new JobResult(job.getId(), attempt.getId(), false, null);
    result.setErrorMessage(errorMsg);
    resultRepository.save(result);

    int affected = markJobFailedIfRunning(job.getId());
    if (affected == 1) {
        eventPublisher.publishEvent(JobEventType.JOB_FAILED, job.getId(), job.getOwnerId(),
            e.getClass().getSimpleName());
        jobFailedCounter.increment();

        Duration duration = Duration.between(attempt.getStartedAt(), attempt.getCompletedAt());
        jobExecutionTimer.record(duration);

        log.warn("Job failed: {} (attempt {}): {}", job.getId(), attempt.getAttemptNumber(), e.getMessage());

        jobRepository.findById(job.getId()).ifPresent(this::handleRetryableFailure);
    } else {
        log.debug("Job failure race detected (job already transitioned): {}", job.getId());
    }
}
```
**Details:** error message truncated to 1000 chars (DB-safe, log-safe, no stack traces persisted); `errorClass` is the simple class name (this is also what flows into the Kafka event `metadata` — error class only, never payloads). The job is re-fetched from the DB before the retry decision so the decision uses the *committed* FAILED row, not the possibly-stale in-memory entity.

## CODE-014 — Automatic retry decision (`JobService.handleRetryableFailure`)

```java
private void handleRetryableFailure(Job job) {
    if (job.getStatus() != JobStatus.FAILED) {
        log.debug("Job {} is not in FAILED state ({}), skipping retry logic", job.getId(), job.getStatus());
        return;
    }

    if (job.getRetryCount() >= job.getMaxRetries()) {
        stateMachine.validateTransition(job.getStatus(), JobStatus.DEAD);
        job.setStatus(JobStatus.DEAD);
        job.setCompletedAt(Instant.now());
        jobRepository.save(job);
        eventPublisher.publishEvent(JobEventType.JOB_DEAD, job.getId(), job.getOwnerId());
        jobDeadCounter.increment();
        log.warn("Job moved to DEAD state (retries exhausted): {}", job.getId());
    } else {
        long backoffMs = calculateBackoff(job.getRetryCount());
        Instant retryAt = Instant.now().plusMillis(backoffMs);

        stateMachine.validateTransition(job.getStatus(), JobStatus.RETRYING);
        job.setStatus(JobStatus.RETRYING);
        job.setRetryCount(job.getRetryCount() + 1);
        job.setScheduledAt(retryAt);
        job.setCompletedAt(null);
        jobRepository.save(job);

        eventPublisher.publishEvent(JobEventType.JOB_RETRYING, job.getId(), job.getOwnerId());
        jobRetriedCounter.increment();

        log.info("Job scheduled for retry: {} (attempt {}, backoff {}ms, scheduled at {})",
            job.getId(), job.getRetryCount(), backoffMs, retryAt);
    }
}
```
**Semantics:** state precondition re-checked (only FAILED proceeds — a CANCELLED/CANCELLED-raced job is skipped). Exhaustion check `retryCount >= maxRetries` **before** incrementing, so `maxRetries=2` means 1 initial run + 2 retries (3 attempts total) then DEAD. Retry path: backoff deadline stored in `scheduledAt` (dual-purposed column: scheduled start time OR backoff deadline), `completedAt` cleared, counter incremented *after* the deadline is computed (so first failure retries after 1 s: `2^0`). The scheduler is what actually re-queues: `RETRYING → (scheduledAt ≤ now) → QUEUED` via `scheduleJob`. **No thread sleeps** — backoff is durable DB state.

## CODE-015 — Exponential backoff (`JobService.calculateBackoff`)

```java
public long calculateBackoff(int retryCount) {
    long baseDelay = 1000L;
    long maxDelay = 30000L;
    long delay = baseDelay * (long) Math.pow(2, retryCount);
    return Math.min(delay, maxDelay);
}
```
Formula: **min(1000 · 2^retryCount, 30 000) ms**, no jitter. Table: retry 0→1 s, 1→2 s, 2→4 s, 3→8 s, 4→16 s, 5+→30 s (capped). Verified by `RetryLogicTest` (9 tests) and `JobServiceIntegrationTest.backoff_*`. Overflow-safe in practice (`retryCount ≤ 10` by validation ⇒ max 2^10·1000). Cap prevents unbounded delays; absence of jitter means synchronized clients could see retry herds (accepted, documented).

**Semantics:** `cancel(true)` interrupts the handler thread (cooperative — `Thread.sleep` throws `InterruptedException`, CPU loops don't notice). ## CODE-023 — Rate limit check (`RateLimitService.checkRateLimit`)

```java
public RateLimitResult checkRateLimit(String userId) {
    try {
        long nowMs = System.currentTimeMillis();
        long windowIndex = nowMs / (WINDOW_SECONDS * 1000);
        long windowStartMs = windowIndex * WINDOW_SECONDS * 1000;
        String currentKey = "rate_limit:" + userId + ":" + windowIndex;
        String previousKey = "rate_limit:" + userId + ":" + (windowIndex - 1);

        List<Long> result = redisTemplate.execute(redisScript,
            Arrays.asList(currentKey, previousKey),
            String.valueOf(maxRequestsPerMinute),
            String.valueOf(WINDOW_SECONDS),
            String.valueOf(nowMs),
            String.valueOf(windowStartMs));

        if (result == null || result.size() != 2) {
            return new RateLimitResult(failOpen, maxRequestsPerMinute,
                failOpen ? maxRequestsPerMinute : 0, WINDOW_SECONDS);
        }

        long allowed = result.get(0);
        long used = Math.max(0, result.get(1));

        if (allowed == 1L) {
            long remaining = Math.max(0, maxRequestsPerMinute - used - 1);
            return new RateLimitResult(true, maxRequestsPerMinute, remaining, 0);
        }
        return new RateLimitResult(false, maxRequestsPerMinute, 0,
            Math.max(1, WINDOW_SECONDS - (nowMs - windowStartMs) / 1000));
    } catch (Exception e) {
        if (failOpen) {
            log.warn("Rate limit check failed, failing open: {}", e.getMessage());
            return new RateLimitResult(true, maxRequestsPerMinute, maxRequestsPerMinute, 0);
        } else {
            log.error("Rate limit check failed, failing closed: {}", e.getMessage());
            return new RateLimitResult(false, maxRequestsPerMinute, 0, WINDOW_SECONDS);
        }
    }
}
```
**Details:** `windowIndex = epochMinutes` — keys rotate every minute; two keys cover the sliding window. The whole decision (read both, compare, increment, expire) happens **inside Redis** — no check-then-act gap. `remaining = limit - used - 1` because this request already consumed one. `Retry-After` = seconds until the current window ends (min 1). Fail-open/closed branch covers Redis outage; note `RateLimitResult` null-shape case also honors the policy.

## CODE-024 — The Lua script (verbatim, annotated)

```lua
local currentKey  = KEYS[1]
local previousKey = KEYS[2]
local limit         = tonumber(ARGV[1])
local windowSeconds = tonumber(ARGV[2])
local nowMs         = tonumber(ARGV[3])
local windowStartMs = tonumber(ARGV[4])

local current  = tonumber(redis.call('GET', currentKey) or '0')
local previous = tonumber(redis.call('GET', previousKey) or '0')

local elapsed = (nowMs - windowStartMs) / 1000
local weight  = 1 - math.max(0, math.min(1, elapsed / windowSeconds))
local used    = current + previous * weight

if used >= limit then
    return {0, used}
end

current = redis.call('INCR', currentKey)
if current == 1 then
    redis.call('EXPIRE', currentKey, windowSeconds * 2)
end
return {1, used}
```
**Line by line:** KEYS[1]/KEYS[2] are the current and previous minute buckets for this user. `elapsed` = how far into the current window we are. `weight` decays linearly from 1 (window just started → previous bucket fully counts) to 0 (window about to end → previous bucket ignored) — this is the sliding-window-counter approximation. `used` = current count + weighted previous count. Deny without incrementing if over limit (denied requests don't consume quota). Otherwise INCR; if this created the key (INCR returned 1) set TTL = 2× window (120 s) so buckets self-clean even if the client goes quiet. Returns `{allowed, used}`. **Atomicity:** Redis executes the script as a single serialized operation — concurrent requests can never both pass the check (this is the property the README calls "no check-then-act race").

## CODE-027 — Kafka deduplication (two layers)
1. **Proactive:** `existsByEventId(eventId)` → skip before insert (cheap, catches sequential redelivery).

## 9.1 Transition table (from `JobStateMachine.VALID_TRANSITIONS` and every caller)

| Current | Allowed next | Trigger (caller) | Code location | Conditions |
|---|---|---|---|---|
| CREATED | SCHEDULED | Job creation with future `scheduledAt` | `JobService.doCreateJob` / `handleIdempotency` | `scheduledAt.isAfter(now)` |
| CREATED | QUEUED | Job creation immediate (or past `scheduledAt`) | same | — |
| CREATED | CANCELLED | User cancels a not-yet-queued job | `JobService.cancelJob` | ownership verified |
| SCHEDULED | QUEUED | Scheduler admits when due | `JobScheduler.scheduleDueJobs` → `JobService.scheduleJob` | `scheduledAt ≤ now` (query-filtered) |
| SCHEDULED | CANCELLED | User cancels a scheduled job | `JobService.cancelJob` | ownership verified |
| QUEUED | RUNNING | **Worker claim (atomic conditional UPDATE)** | `WorkerPool.executeWithClaim` → `JobService.claimJob` → `JobRepository.claimJob` | SQL predicate `status='QUEUED'` — exactly one winner |
| QUEUED | CANCELLED | User cancels a queued job | `JobService.cancelJob` | ownership verified (race window: claim may win first ⇒ cancel gets 0-row effect at claim, or cancel wins and claim returns false) |
| RUNNING | SUCCESS | Handler returned normally, atomic update wins | `JobService.completeJob` → `markJobSuccessIfRunning` | SQL predicate `status='RUNNING'` |
| RUNNING | FAILED | Handler threw OR timed out, atomic update wins | `failJobAndRetry` / `handleTimeout` → `markJobFailedIfRunning` | SQL predicate `status='RUNNING'` |
| RUNNING | RETRYING | **exists in the SM table but is never executed in code** — the runtime path is RUNNING→FAILED→(decision)→RETRYING; `handleRetryableFailure` is only ever invoked on a FAILED job | (none — table-only edge) | — |
| FAILED | RETRYING | Retry budget remains | `JobService.handleRetryableFailure` | `retryCount < maxRetries`; sets `scheduledAt = now + backoff` |
| FAILED | DEAD | Retry budget exhausted | same | `retryCount ≥ maxRetries` |
| RETRYING | QUEUED | Scheduler sees backoff deadline passed | `JobScheduler` → `JobService.scheduleJob` | query-filtered `scheduledAt ≤ now` |
| SUCCESS | — (terminal) | — | — | — |
| DEAD | — (terminal) | — | — | — |
| CANCELLED | — (terminal) | — | — | — |
| DEAD → QUEUED | **special guarded operation outside the map** | Admin `POST /api/jobs/{id}/recover` OR owner `POST /api/jobs/{id}/retry` on a DEAD job | `JobService.recoverJob` / `retryJob` via `stateMachine.validateRecovery` | requires DEAD; resets retryCount=0, completedAt=null; role/ownership enforced upstream |

## 9.3 Enforcement analysis

- **Who may transition:** only `JobService` methods mutate status at the service layer; `JobScheduler` and `WorkerPool` act through it. No controller or handler touches status directly.
- **Centralized?** Yes for all *entity-save* transitions (`JobStateMachine.validateTransition`/`validateRecovery` precede every `setStatus` in the service).
- **Deliberate exceptions (direct repository updates):** the three atomic conditional UPDATEs (`claimJob`, `markJobSuccessIfRunning`, `markJobFailedIfRunning`) bypass the in-memory SM. This is **intentional and correct**: under concurrency, checking the status in Java and then writing it is exactly the TOCTOU race the design eliminates; the SQL `WHERE status = 'X'` clause *is* the transition guard, enforced atomically by PostgreSQL. Every edge they perform (QUEUED→RUNNING, RUNNING→SUCCESS, RUNNING→FAILED) is a legal edge in the map.
- **How invalid transitions are prevented:** service-level paths throw `InvalidJobTransitionException` (→ HTTP 409, e.g., double-cancel, retry of a QUEUED job, recovery of a non-DEAD job). Concurrent paths are prevented by the conditional-update predicate, not by exceptions.
- **Direct repository updates list:** the three above. All other status writes go through entity `save()` after SM validation.

# 11. SCHEDULER DEEP DIVE

| Aspect | Actual implementation |
|---|---|
| Mechanism | Spring `@Scheduled` on `JobScheduler.scheduleDueJobs()`; `@EnableScheduling` on the application class |
| Annotation | `@Scheduled(fixedDelayString = "${app.scheduler.interval-seconds:5}", initialDelay = 5000)` |
| Polling interval | **Documented intent:** 5 s. **Actual:** `fixedDelayString` interprets the plain number as **milliseconds** → the loop fires every **5 ms** (no `application-docker.properties` exists; `SPRING_PROFILES_ACTIVE=docker` selects nothing). Classified as a BUG (unit mismatch) in §50/§56 — functionally safe (fixedDelay prevents overlap; dedup + atomic claim absorb re-submission) but with ~200× the intended DB polling load and ±5 ms precision instead of ±5 s |
| Batch size | `app.scheduler.batch-size=50` → `PageRequest.of(0, 50)` on both queries |
| Due-job query | `findDueJobs`: `status='CREATED' OR (status='SCHEDULED' AND scheduledAt<=:now) OR (status='RETRYING' AND scheduledAt<=:now) ORDER BY priority ASC, scheduledAt ASC NULLS LAST` |
| Statuses picked | CREATED (any), SCHEDULED (due), RETRYING (backoff expired). **QUEUED is NOT picked by this query** — QUEUED jobs are handled by the second phase |
| Entry to queue | `JobService.scheduleJob` (SM-validated → status=QUEUED + JOB_QUEUED event) then `workerPool.submit(job)` |
| Direct execution? | **No.** The scheduler never executes handlers (Javadoc + `scheduler_doesNotExecuteLongRunningJobs` test) |
| Duplicate admission | Three guards: (1) `fixedDelay` = no overlapping cycles in-JVM; (2) `WorkerPool.submittedJobIds` set (per-instance in-flight dedup); (3) the DB atomic claim is the final arbiter — even if a job is submitted twice, only one claim wins |
| Multi-instance | NOT safe as-is: each instance would run its own poller and dedup set. Correctness is preserved by the atomic claim (no double execution), but work would be redundantly dispatched; no leader election / distributed lock (`NOT IMPLEMENTED`) |
| Precision | ±interval. With the ms-bug: ±5 ms effectively; README claims ±5 s |
| Failure scenarios | Any exception in one job's schedule/submit is caught per-job (loop continues); a whole-cycle exception is caught at the top (timer survives); DB down → exception logged every tick, recovery automatic when DB returns |
| Race conditions | scheduler vs cancel: `scheduleJob` re-validates the transition — a CANCELLED job fails the check (exception logged, no state damage). scheduler vs worker: job fetched as RETRYING may already be QUEUED → `scheduleJob` would attempt RETRYING→QUEUED again... actually each cycle re-reads fresh rows via the service; the dedup set + claim make redundant submissions harmless |
| Limitations | no jitter; no SKIP LOCKED batch claiming; single instance; poll query cost scales with due-job count |

# 12. QUEUE + PRIORITY DEEP DIVE (actual implementation)

**The ACTUAL queue is a two-layer construction, not a JMS/PriorityBlockingQueue:**

1. **Durable layer — PostgreSQL `jobs` table.** "Waiting in queue" = row with `status='QUEUED'` (or `RETRYING` with a future backoff deadline). Survives restarts; the scheduler re-discovers it. This is the single source of truth.
2. **Dispatch layer — in-memory `ThreadPoolExecutor` queue.** `LinkedBlockingQueue(100)` holding `Runnable`s (FIFO). Capacity 100; when full, `CallerRunsPolicy` executes the task on the *scheduler* thread — i.e., **admission blocks the poller instead of dropping jobs** (jobs are never lost, only delayed).

**How priority is determined:** ordering happens **in SQL** — both `findDueJobs` and `findQueuedJobsForDispatch` end with `ORDER BY j.priority ASC, j.scheduledAt ASC NULLS LAST`. HIGH(1) sorts before MEDIUM(5) before LOW(10); ties broken FIFO by `scheduledAt` (nulls last, so jobs that never set it come last). The fetched batch is then submitted to the executor in that order; within one batch the executor's FIFO queue preserves it.

**Not in-memory priority:** between two SQL fetches a newly created HIGH job cannot overtake an already-submitted LOW task — the in-memory buffer is FIFO. Priority is re-applied at every scheduler fetch (with the ms-bug that is every ~5 ms; at the intended 5 s cadence it would be every 5 s).

| Question | Answer (evidence) |
|---|---|
| Where do jobs wait? | `jobs` rows in QUEUED/RETRYING state; then Runnables in the executor's `LinkedBlockingQueue(100)` |
| Queue capacity | 100 executor tasks (not 100 jobs — each task is one claimed-or-unclaimed job execution attempt); DB-side "capacity" unbounded |
| Queue full | `CallerRunsPolicy`: scheduler thread executes the task synchronously → natural backpressure, no rejection/loss |
| Durable? | The *DB* layer yes; the executor queue **no** |
| Restart behavior | Executor queue contents vanish; all QUEUED/RETRYING rows are re-fetched by the scheduler and re-submitted — no job loss. A job that was RUNNING at crash time stays RUNNING forever (no lease/timeout sweeper for orphaned RUNNING rows — see §34/§40) |
| DB vs in-memory division | DB = state & recovery truth; memory = dispatch buffer & dedup set. The dedup set is per-instance (limitation #6 in README) |

## 13.2 Atomic job claiming — the core guarantee

```sql
-- JobRepository.claimJob (JPQL shown in §8/CODE-009; executed as):
UPDATE jobs SET status='RUNNING', started_at=:now WHERE id=:jobId AND status='QUEUED'
```
- **Transaction boundary:** `@Transactional` on the repository method itself — its own short transaction, independent of the (non-transactional) execution path. Comment in `JobRepository` states this explicitly.
- **Race walkthrough:** Worker A and Worker B both hold the same Job object (status QUEUED). A's UPDATE acquires the row lock; the WHERE predicate is evaluated against the *current committed* row → true → status set to RUNNING, 1 row affected. B's UPDATE waits on the lock; when it proceeds the predicate is re-evaluated → status is RUNNING → 0 rows affected. **A executes, B exits silently.**
- **Why duplicate workers cannot both win:** PostgreSQL evaluates the predicate and applies the update atomically under the row lock; there is no interleaving where both read QUEUED and both write RUNNING.
- **Affected-row count contract:** 1 = ownership; 0 = lost (already claimed / cancelled / in another state).
- **Optimistic locking relationship:** `Job.version` (`@Version`) exists, but the correctness-critical paths deliberately do NOT rely on optimistic-retry loops — they use conditional UPDATEs (last-write-wins with a state predicate). A plain entity save on a stale version would throw `OptimisticLockException` (→ 500 via generic handler), but no production path triggers it because status changes race through the conditional updates instead.

## 13.4 Other concurrency controls
- **Execution parallelism:** handlers run on the common ForkJoinPool via `CompletableFuture.supplyAsync`; the 5 worker threads *block* on `future.get` — so true handler parallelism is bounded by the FJP (CPU×2ish) and DB parallelism by the 5 claimers.
- **Per-instance dedup:** `submittedJobIds` prevents the same tick's due-loop and queued-loop from double-submitting; removed in `finally`.
- **Completion races:** guarded by `markJobSuccessIfRunning`/`markJobFailedIfRunning` (§32 race #2).

# 14. RETRY SYSTEM

| Aspect | Actual implementation |
|---|---|
| Counters | `job.retryCount` (attempts *retried*), `job.maxRetries` (user-set 1–10, default 3) |
| What counts as an attempt | One execution of the handler = one `job_attempts` row; attemptNumber = retryCount+1 at execution time. Both exception failures and timeouts consume the budget |
| Retryable failure | Everything: handler exception (any type), timeout (`TimeoutException` path). No non-retryable classification exists (`NOT IMPLEMENTED` — no error-type filtering) |
| Flow | RUNNING --(atomic)--> FAILED → `handleRetryableFailure`: retryCount < maxRetries → RETRYING (deadline set) → scheduler → QUEUED → claim → next attempt; else → DEAD |
| Backoff formula | `min(1000 · 2^retryCount, 30000)` ms; base 1 s; cap 30 s; **no jitter**; computed BEFORE incrementing retryCount (first retry waits 1 s) |
| Scheduler interaction | `scheduledAt` holds the backoff deadline; `findDueJobs` includes RETRYING rows with `scheduledAt ≤ now`; `scheduleJob` performs the SM-validated RETRYING→QUEUED transition |
| Worker sleeps? | **No.** The worker thread returns immediately after persisting RETRYING state; backoff is DB state, not thread blocking (explicitly documented in `handleRetryableFailure` Javadoc) |
| retryCount reset | Manual retry (FAILED→…→QUEUED) and DEAD recovery both set retryCount=0 and clear completedAt (`JobService.retryJob` / `recoverJob`) |
| Manual retry | `POST /api/jobs/{id}/retry` — owner-checked; FAILED goes through the legal two-step validation (FAILED→RETRYING→QUEUED validated, then saved once as QUEUED); DEAD goes through `validateRecovery`; anything else → 409 |
| Admin recovery | `POST /api/jobs/{id}/recover` — ADMIN URL rule; DEAD→QUEUED with counters reset |
| Exhaustion → DEAD | When `retryCount >= maxRetries` at failure time; DEAD rows carry completedAt; JOB_DEAD event; `jobs_dead` counter |
| Cost cap | Worst case per job: (maxRetries+1) executions + Σ backoff ≈ 1+2+4+…capped ≤ ~10·30 s + 10 executions |

Actual code: CODE-013 (failure persistence), CODE-014 (decision), CODE-015 (formula). Tests: `RetryLogicTest` (9), `JobServiceIntegrationTest.automaticRetry_*` (4), `timeout_retriesExhausted_becomesDead`, `retryJob_deadJob_recoversThroughStateMachine`.

# 15. TIMEOUT SYSTEM

| Aspect | Actual implementation |
|---|---|
| Timeout field | `job.timeoutSeconds` (default 300; DTO-validated 1–3600) |
| Mechanism | `CompletableFuture.supplyAsync(handler)` + blocking `future.get(timeoutSeconds, TimeUnit.SECONDS)` on the worker thread |
| On timeout | `catch (TimeoutException)` → `future.cancel(true)` (interrupt) → `handleTimeout(job, attempt)` → attempt TIMED_OUT + failure result + atomic `markJobFailedIfRunning` → JOB_FAILED(metadata="TimeoutException") → same retry/DEAD decision as any failure |
| Interruption semantics | `cancel(true)` sets the handler thread's interrupt flag. `Thread.sleep`-based handlers exit promptly (InterruptedException). CPU-bound or interrupt-ignoring handlers **keep running** — Java has no safe forced termination |
| **COOPERATIVE INTERRUPTION — what is NOT guaranteed** | The system guarantees: (a) timeout *detection* at exactly timeoutSeconds, (b) the job's DB state leaves RUNNING via the atomic update, (c) the attempt is recorded TIMED_OUT, (d) retry/DEAD proceeds. It does NOT guarantee the handler's code has stopped — a timed-out handler may keep consuming CPU/memory and *cannot* publish side effects to the job state (it lost the race), but external side effects it performs (none in this codebase's simulated handlers) would proceed |
| Attempt status | `TIMED_OUT` (distinct enum value from FAILED), errorClass `TimeoutException`, message `"Job execution timed out after N seconds"` |
| Retry interaction | Timeout is just a failure — consumes retry budget identically (`timeout_retriesExhausted_becomesDead` proves DEAD via timeouts) |
| Race: timeout vs successful completion | Both paths end in an atomic conditional UPDATE keyed on `status='RUNNING'`; **exactly one wins** (`affected==1`), the loser logs "race detected" and persists only its attempt/result rows. The job's terminal state is decided by whoever wins the DB race — see §32 race #2 |
| Race: timeout vs failure | Same guard (`markJobFailedIfRunning`) — a handler that throws at t=timeout-ε and a timeout at t=timeout cannot both transition the job |
| Handler-thread pool note | Handlers run on the ForkJoinPool commonPool (not the worker pool); a stuck handler leaks one FJP thread until it finishes — bounded by the common pool size, not by job limits |

Actual code: CODE-010 (executeJob), CODE-016 (handleTimeout). Tests: `timeout_longRunningJob_timesOut` (REPORT + 1 s → TIMED_OUT attempt, job FAILED/RETRYING), `timeout_withRetries_retriesAfterTimeout`, `timeout_retriesExhausted_becomesDead`; runtime scenario E.

# 16. IDEMPOTENCY

## 16.1 Mechanics

| Aspect | Actual implementation |
|---|---|
| Transport | `Idempotency-Key` HTTP header on `POST /api/jobs` (optional; blank ⇒ normal creation) |
| Storage | Two unique constraints: `jobs.idempotency_key` (unique index `idx_job_idempotency_key`) and `idempotency_records.idempotency_key` (unique index `idx_idempotency_key`) |
| Flow (no record) | insert job (with key) → insert `IdempotencyRecord(key, jobId, ownerId)` → events/counter → 201 |
| Flow (record exists, same owner) | return the existing job — **the original request's data wins** (second request's name/type ignored) |
| Flow (record exists, other owner) | `DuplicateJobException` → 409 neutral conflict, no existence oracle |
| Insert race | loser's `jobs` INSERT violates the unique constraint → `DataIntegrityViolationException` → catch → re-lookup by key → same-owner: return winner's job; other-owner: 409; lookup miss: rethrow (500) |
| Concurrency proof | 20-thread and 50-thread same-key tests: all success responses carry the same single job id (`IdempotencyConcurrencyTest`); runtime scenario F: 5 parallel → all 201, exactly 1 row with the key |
| Key scope | **owner-scoped**: uniqueness is global, but *resolution* is per-owner (same key + different owner ≠ replay) |
| Expiry/TTL | **None** — records live forever (`NOT IMPLEMENTED`; acceptable for demo, noted §40) |
| Restart survival | yes — DB-backed, not cache |
| Response shape | replay returns the same `JobResponse`; no replay-detection header (`NOT IMPLEMENTED`) |

## 16.2 REQUEST idempotency vs EXECUTION idempotency (critical distinction)

- **REQUEST idempotency (IMPLEMENTED & TESTED):** identical POSTs with the same key+owner produce exactly one job resource. This is creation-layer deduplication only.
- **EXECUTION idempotency (NOT IMPLEMENTED):** the platform provides **at-least-once execution**, and the README says so explicitly ("No Exactly-Once Execution: At-least-once semantics only"). A crash between the handler's side effects and the state persistence (or a retry after a partial failure) can execute the handler twice. The atomic claim prevents *concurrent* duplicate execution, but not *temporal* duplication across crashes. Handlers should therefore be idempotent (README "Key Design Decisions"). Do not claim exactly-once for this project — no outbox, no dedup at execution layer, no idempotency tokens on execution.

## 16.3 Security dimensions
- Cross-user key reuse → neutral 409 (no leak, no oracle) — CODE-003.
- Response of a replay returns the owner's own job only.
- The key is stored in `JobResponse` (owner-visible; fine — it's their key).

```
4. Controller receives Authentication; authentication.getName() = username = ownerId used

```

## 19.2 Registration / login / hashing
- `POST /api/auth/register`: `existsByUsername` → 409 (empty body); **role field from `RegisterRequest` is ignored — hard-coded `"USER"`** (comment in `AuthController` documents the privilege-escalation rationale; `DataInitializer` is the only ADMIN source, from env/config only). Password hashed with `BCryptPasswordEncoder` before save. JWT issued immediately.
- `POST /api/auth/login`: `AuthenticationManager` (DaoAuthenticationProvider machinery) → `CustomUserDetailsService` + BCrypt match; failure → `BadCredentialsException` → 401 "Invalid username or password" (uniform message: no user-existence oracle).
- Token: HS256, sub=username, iat/exp, 24 h expiry, secret from `app.jwt.secret` (dev default base64 — DEVELOPMENT ONLY, §32). No refresh; no revocation; stateless.
- Roles: only `USER` and `ADMIN` exist. `@EnableMethodSecurity` + `@PreAuthorize("hasRole('ADMIN')")` on the admin list endpoint (redundant with the URL rule — defense in depth). `/recover` relies on the URL rule only.

# 20. REDIS DEEP DIVE

**EXACT USAGE: rate limiting only.** Source search confirms the only Redis interactions are `StringRedisTemplate.execute(luaScript)` and two `opsForValue().get()` calls in the (main-flow-unused) `getRemainingRequests`. **Redis is NOT the source of truth for job state** — no job/attempt/result data is ever written to or read from Redis.

| Aspect | Actual implementation |
|---|---|
| Client | Spring Data Redis (`spring-boot-starter-data-redis`, Lettuce default) via `StringRedisTemplate` |
| Key format | `rate_limit:{userId}:{windowIndex}` where `windowIndex = floor(epochMillis / 60000)`; plus `rate_limit:{userId}:{windowIndex-1}` |
| TTL | `EXPIRE windowSeconds*2` = **120 s**, set only when INCR creates the bucket (script line `if current == 1`) |
| Algorithm | Sliding-window counter: `used = current + previous × (1 − elapsed/60)`, i.e., linearly decaying weight of the previous bucket |
| Atomicity | Entire check-and-increment is ONE Lua script executed atomically by Redis — concurrent requests cannot both pass the limit check (no check-then-act race); the fix history (README Phase-3 #2) records that this replaced a single-bucket fixed window |
| Limit | 100 requests/minute/user (`app.rate-limit.requests-per-minute`); keyed by username |
| Denial handling | Over-limit requests are NOT counted (no INCR) — denied requests don't consume quota |
| HTTP surface | 429 via `RateLimitException`; headers `Retry-After` (60 fixed in handler / computed in RateLimitResult but the handler's fixed 60 wins for the exception path) and `X-RateLimit-Remaining: 0`; success responses carry `X-RateLimit-Limit` and `X-RateLimit-Remaining` |
| Applied where | **Only** `POST /api/jobs` (`JobController.checkRateLimit`) — listing/detail/cancel/etc. are NOT rate-limited |
| Fail-open/fail-closed | `app.rate-limit.fail-open=true` default: Redis exception → allow all (warn log). `false` → deny all with Retry-After=60 (error log). Null/malformed script result honors the same flag |
| Metrics | `rate_limit.rejections` Counter incremented in the controller when denying (this was dead code before the audit fix — registered but never incremented; now wired) |
| Where applied in lifecycle | before `jobService.createJob`; rejection happens before validation-visible work (rate-limit check precedes handler-registry/idempotency logic in the controller) |

## 21.2 Event structure and all event types

```json
{
  "eventId": "b1c2d3e4-...",          // UUID — set in JobEvent no-arg ctor; dedup anchor
  "eventType": "JOB_FAILED",          // enum name
  "jobId": "3f1c2a...",               // UUID

```
All 8 event types (enum `JobEventType`), with emitters:
| Event | Emitted by | Metadata |
|---|---|---|
| JOB_CREATED | `doCreateJob`, `handleIdempotency` (fresh create only) | null |
| JOB_QUEUED | `doCreateJob` (immediate), `handleIdempotency`, `scheduleJob` (SCHEDULED/RETRYING→QUEUED), `retryJob`, `recoverJob` | null |

| JOB_DEAD | `handleRetryableFailure` (exhaustion) | null |
| JOB_CANCELLED | `cancelJob` | null |

## 21.3 Why Kafka for lifecycle events / why NOT as the task queue
- **For events:** decoupled, replayable audit; at-least-once delivery; partition-local ordering per job; the consumer (audit persistence) can fail or lag without touching execution.
- **Not the task queue:** execution requires a single-winner transition (QUEUED→RUNNING) with retry/dead state — a DB row provides compare-and-swap semantics natively, whereas Kafka consumption is at-least-once ⇒ duplicate *executions* would be possible. The design deliberately keeps Kafka out of the correctness path (README: "Kafka is Async — event publishing failure does not affect job state"). `executeJob` never touches Kafka for dispatch; `WorkerPool` + `JobRepository.claimJob` do the dispatching.
- **No transactional outbox (`NOT IMPLEMENTED`):** a crash between the DB write and the async Kafka send can lose an event (audit gap); conversely no double-emission risk since events are published after successful state writes.

# 38. INTERVIEW KNOWLEDGE BASE

Format per item: **Q / Short / Detailed + project specifics / Tradeoff / Limitation.** All answers below are grounded in this codebase.

### LEVEL 1 — Basic
**Q: What does the project do?** Short: schedules and executes background jobs reliably with a REST API. Detailed: users POST jobs; PostgreSQL stores them; a poller queues due jobs; a 5-thread pool claims (atomically) and runs simulated handlers with timeout, retry/backoff, DEAD/recovery; Kafka events feed an audit table; JWT+rate limiting secure the API; Prometheus/Grafana observe it. Class: `JobService`, `JobScheduler`, `WorkerPool`.

**Q: What is a Job here?** A row in `jobs`: owner, type (5 fixed types), priority (3 levels), status (9 states), payload ≤10 k chars, retry budget, timeout, optional idempotency key. Entity: `Job`.

**Q: What technologies and why?** Spring Boot (fast, integrated); PostgreSQL (relational + row locks → atomic claiming); Redis (atomic Lua rate limiting); Kafka (decoupled lifecycle events + audit); JWT (stateless auth); Micrometer/Prometheus/Grafana (metrics); React/Vite (admin UI); Docker Compose (reproducible infra).

**Q: What happens after POST /api/jobs?** filter chain → rate limit (Redis Lua) → validation → handler-registry check → idempotency branch → INSERT `jobs` (+`idempotency_records`) → Kafka JOB_CREATED/QUEUED → `jobs_created_total`++ → 201 with `X-RateLimit-*`.

### LEVEL 2 — Intermediate
**Q: How does the state machine work?** Centralized `EnumMap` of allowed edges in `JobStateMachine`; every entity-level transition validates first; the three hot-path transitions are enforced by SQL predicates instead (below). 36 tests pin the map.

**Q: How does scheduling work?** `@Scheduled(fixedDelayString)` poller → `findDueJobs` (CREATED / due SCHEDULED / due RETRYING, priority-ordered) → `scheduleJob` (SM-validated → QUEUED + event) → `workerPool.submit`. Batch 50. The scheduler never executes.

**Q: How does priority work?** Numeric priority: HIGH=1 < MEDIUM=5 < LOW=10; both dispatch queries `ORDER BY priority ASC, scheduledAt ASC NULLS LAST`; ordering happens in SQL so it's global, then executor FIFO within a batch.

**Q: How does queueing work?** Two layers: durable QUEUED rows in Postgres (truth) + in-memory `LinkedBlockingQueue(100)` in the executor (buffer). Full queue → CallerRunsPolicy backpressure. Restart re-discovers QUEUED rows.

**Q: How does retry work?** Failure/timeout → attempt row (FAILED/TIMED_OUT) → atomic RUNNING→FAILED → `handleRetryableFailure`: retryCount<max ⇒ RETRYING with `scheduledAt=now+min(1s·2^n,30s)`; scheduler re-queues when deadline passes; else DEAD.

**Q: How does timeout work?** `CompletableFuture.supplyAsync(handler)` + `future.get(timeout, SECONDS)`; on TimeoutException `cancel(true)` (interrupt) + TIMED_OUT attempt + same failure pipeline. Cooperative: handler code may keep running.

**Q: How does JWT auth work?** Register/login → HS256 token {sub, iat, exp, 24 h}. Each request: filter verifies signature+exp, loads user from DB for `ROLE_*` authorities, sets SecurityContext. No role claim in token ⇒ role changes apply immediately.

**Q: How is ownership enforced?** Every job-scoped service method compares `job.ownerId` with the JWT subject; mismatch → 404 (identical to not-found) on get/cancel/retry/attempts/result.

### LEVEL 3 — Advanced
**Q: How do you prevent duplicate execution?** Three layers: (1) per-instance in-flight dedup set; (2) **atomic conditional UPDATE claim** — `UPDATE ... WHERE status='QUEUED'` returning affected rows; exactly one worker gets 1; (3) conditional completion updates (`WHERE status='RUNNING'`) so a timeout cannot race a success into double-transition. Proof: 10-thread race test → 1 winner.

**Q: Why is the claim @Transactional on the repository, not the service?** `executeJob` is intentionally non-transactional (a 1-h handler must not pin a pooled connection); declaring TX on the repository methods gives each atomic update its own short transaction, so correctness never depends on the caller's transaction. (Also: self-invocation would make service-level annotations inert on private helpers.)

**Q: Why is idempotency safe under concurrent duplicates?** Unique constraint on `jobs.idempotency_key` is the arbiter; the loser catches `DataIntegrityViolationException` and re-reads the winner (the method is deliberately non-transactional so the constraint violation doesn't mark the surrounding TX rollback-only). Keys are owner-scoped: different owner → neutral 409.

**Q: How does Redis rate limiting avoid races?** One Lua script performs GET both buckets → weighted compare → INCR → EXPIRE atomically; Redis single-threaded execution means no check-then-act gap. Sliding-window-counter (previous bucket × linear weight) avoids the 2× fixed-window boundary burst. Fail-open default keeps availability when Redis dies.

**Q: Why Kafka and not Kafka-as-queue?** Execution needs single-winner semantics and rich per-job state — the DB gives compare-and-swap natively; Kafka consumption is at-least-once, which would risk duplicate *executions*. Kafka is therefore the event spine (audit), where at-least-once + unique eventId = exactly-once rows.

**Q: Explain the timeout-vs-completion race.** Worker blocked in `future.get` times out while the handler returns in parallel. Both paths end in conditional UPDATEs predicated on RUNNING; only one affected-row==1 wins; the loser's attempt/result rows persist but the job's state stays consistent. No lock in Java needed — the DB decides.

### LEVEL 4 — Senior distributed-systems
**Q: Is execution at-least-once or exactly-once?** At-least-once. Concurrent duplicates are impossible (claim), but crash between handler side effects and state persistence, or post-crash re-dispatch, can duplicate work. Handlers should be idempotent. (README agrees; do not claim exactly-once.)

**Q: What happens if the app crashes mid-execution?** QUEUED/RETRYING rows are re-discovered and re-run. A row left RUNNING is orphaned forever (no lease/sweeper) — the platform's biggest operational gap; a fix would be a startup sweeper transitioning stale RUNNING rows to FAILED.

**Q: How would you scale this?** (a) fix scheduler unit bug; (b) add leader election or partition-sharded pollers (SKIP LOCKED batch claiming); (c) stateless API tier behind LB (JWT already stateless; Redis limiter is shared); (d) scale workers by making the pool per-node with DB claiming as sole arbiter (already the case); (e) Kafka partitions scale the audit consumer; (f) Postgres read replicas for queries.

**Q: What's your biggest limitation?** Orphaned RUNNING jobs after crash + no distributed scheduling; also exactly-once is out of scope by design.

**Q: How do you know the atomic claim really works?** A 10-thread CountDownLatch race test asserts successCount==1; the guarantee is the database's row lock + predicate, not JVM constructs; it survives restarts and multi-instance by construction.

# 48. GLOSSARY (simple meaning → meaning in THIS project)

| Term | Simple | In this project |
|---|---|---|
| Job | unit of background work | row in `jobs` (owner, type, priority, status, payload, retry/timeout config, optional idempotency key) |
| Task | work performed | the simulated handler execution for a job |
| Scheduler | triggers work at times | `JobScheduler` poller admitting due CREATED/SCHEDULED/RETRYING rows to QUEUED |
| Queue | waiting line | two-layer: QUEUED rows in Postgres (durable truth) + executor `LinkedBlockingQueue(100)` (dispatch buffer) |
| Worker | executes work | one of 5 `job-worker-N` threads in the fixed `ThreadPoolExecutor` |
| Handler | does the actual work | `JobHandler` impl (5 simulated: DEMO_TASK/REPORT/DATA_CLEANUP/EMAIL/FAILING) |
| Attempt | one execution try | `job_attempts` row (STARTED→COMPLETED/FAILED/TIMED_OUT), attemptNumber=retryCount+1 |
| Result | outcome | `job_results` row with payload or error |
| Priority | importance order | HIGH(1)/MEDIUM(5)/LOW(10); SQL `ORDER BY priority ASC` |
| Retry | run again after failure | FAILED→RETRYING→(scheduler)→QUEUED, budget `maxRetries` 1–10 |
| Backoff | wait between retries | min(1000·2^n, 30000) ms stored in `scheduledAt`; no thread sleeping |
| Timeout | max runtime | `future.get(timeoutSeconds)`; TIMED_OUT attempt; cooperative interrupt |
| Idempotency | same request ⇒ same effect | `Idempotency-Key` header + unique DB keys, owner-scoped replay (request-level only) |
| Atomic claim | single winner take | `UPDATE ... WHERE status='QUEUED'` returning 1/0 |
| CAS | compare-and-swap | the conditional UPDATE pattern above (DB-enforced) |
| State machine | legal status changes | `JobStateMachine` EnumMap + SQL predicates; 9 states, 3 terminals |
| DEAD | permanent failure | terminal state after budget exhaustion; exit via `validateRecovery` |
| Recovery | revive dead work | ADMIN `/recover` or owner retry on DEAD → QUEUED, retryCount=0 |
| JWT | signed token | HS256, sub=username, 24 h; no role claim (role from DB per request) |
| RBAC | role-based access | USER/ADMIN; URL rules + `@PreAuthorize` |
| Ownership | record belongs to user | `Job.ownerId == JWT subject` or 404 |
| Rate limiting | request throttling | Redis Lua sliding-window counter, 100/min/user, 429+headers, fail-open |
| Sliding window | smooth rate window | current bucket + weighted previous bucket (weight=1−elapsed/60) |
| Kafka | event log | topic `job-lifecycle-events`; events only, not the task queue |
| Producer | sends events | `JobEventPublisher` (async, best-effort, key=jobId) |
| Consumer | reads events | `JobEventConsumer` (group `job-platform-audit-consumer`) |
| Event | state-change notification | `JobEvent` JSON (eventId, type, jobId, ownerId, ts, correlationId, metadata=error class) |
| Deduplication | ignore repeats | `existsByEventId` + unique `job_audit_events.eventId` |
| Audit event | persisted history | append-only row per received event |
| Micrometer | metrics facade | 7 counters, 1 percentile timer, 2 gauges, `@Timed` |
| Prometheus | metrics DB | scrapes `/actuator/prometheus` every 15 s |
| Grafana | dashboards | provisioned "Job Platform Overview" (10 panels) |
| CallerRunsPolicy | backpressure | executor-queue-full → submitting (scheduler) thread runs the task |
| Optimistic locking | version check on write | `Job.version` `@Version` present; hot paths use CAS updates instead |
| At-least-once | may repeat, never silently lose | execution AND Kafka semantics here |

- **Project:** Distributed Job Scheduling & Task Execution Platform (`com.distributed:job-platform:1.0.0`) — Spring Boot 3.2.5 / Java 17 monolith + React 18/Vite SPA + 6-service Docker Compose (PostgreSQL 16, Redis 7, Kafka 3.6 KRaft, Prometheus, Grafana).
- **Core model:** PostgreSQL = source of truth and concurrency coordinator. `@Scheduled` poller (⚠ runs every 5 ms due to a ms/seconds unit bug) admits due jobs (CREATED/SCHEDULED-due/RETRYING-due) to QUEUED. `ThreadPoolExecutor(5,5,LBQ(100),CallerRuns)` workers claim via atomic `UPDATE ... WHERE status='QUEUED'` (one winner guaranteed), execute handlers on the ForkJoinPool with `future.get(timeout)`; success/failure/timeout are atomic conditional updates on RUNNING; failures retry with min(1s·2^n,30s) backoff via RETRYING+`scheduledAt`, then DEAD; admin `/recover` (or owner retry) revives DEAD.
- **Key classes:** `JobService` (696-line core), `JobRepository` (3 CAS queries), `JobStateMachine`, `JobScheduler`, `WorkerPool`, `RateLimitService` (Lua), `JobEventPublisher/Consumer`, `JwtTokenProvider/Filter`, `SecurityConfig`, `GlobalExceptionHandler`.
- **APIs:** /api/auth/{register,login,me}; /api/jobs CRUD+lifecycle (create/list/get/cancel/retry/attempts/result), ADMIN recover + admin list; rate-limited create with `Idempotency-Key`; ownership → 404 masking.
- **Tables:** jobs, job_attempts, job_results, idempotency_records, job_audit_events, users (Hibernate `ddl-auto=update`; unique keys on idempotencyKey ×2, eventId, username).
- **Security:** HS256 JWT 24 h (sub-only; role from DB), BCrypt, USER/ADMIN, registration can never mint ADMIN, 400/401/403/404/409/429 semantics.
- **Redis:** rate limiting only (100/min/user, atomic Lua sliding window, fail-open); NOT job-state storage.
- **Kafka:** 8 lifecycle event types → topic `job-lifecycle-events` (3 partitions) → audit consumer (group `job-platform-audit-consumer`) persists idempotently by unique eventId.
- **Observability:** Micrometer (7 counters, p50/95/99 timer, 2 gauges, @Timed×8) → Prometheus (15 s) → Grafana 10-panel "Job Platform Overview".
